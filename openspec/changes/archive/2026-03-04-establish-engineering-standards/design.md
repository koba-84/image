## Context

現状は実験用ノートブックやスクリプトを自由形式で追加できる一方、再現に必要な情報やGit履歴の粒度が人依存である。OpenSpecを規約の一次ソースにし、提案から実装まで同一基準で運用する。

## Goals / Non-Goals

**Goals:**
- コーディング規約とGit規約をOpenSpec設定に集約する
- 規約を仕様シナリオとして検証可能にする
- 画像AI検証で重要な再現性・安全性・追跡可能性を標準化する

**Non-Goals:**
- CI/CDパイプライン実装の導入
- 既存コードの大規模リファクタ
- モデル品質ベンチマーク手法そのものの確定

## Decisions

1. 規約の実体は `openspec/config.yaml` に置き、artifact作成時に常時参照させる
   - 代替案: 別ドキュメント管理
   - 採用理由: OpenSpecワークフローと分離せず、仕様駆動で一貫適用できる
2. Git規約は Conventional Commits を採用し、破壊的変更の明示を必須化する
   - 代替案: 自由記述コミット
   - 採用理由: 変更意図の機械可読性とレビュー効率が高い
3. 画像AI特有の再現性要件(シード・モデル版・パラメータ記録)を必須項目として定義する
   - 代替案: 任意記録
   - 採用理由: 再現実験の失敗率を下げ、比較検証を可能にする
4. 自律実装のGit運用は「作業ブランチへのpush + PR作成」を必須化し、main直pushを禁止する
   - 代替案: 自律pushをmainへ直接許可
   - 採用理由: Branch protection（PRレビュー/必須status checks）と整合し、誤投入リスクを下げる
5. 自律PR作成時の認証は最小権限を原則とし、`contents:write` と `pull-requests:write` を基準にする
   - 代替案: repo全権限トークン
   - 採用理由: GitHubの最小権限原則に沿って秘密情報漏えい時の被害面積を縮小する

## Risks / Trade-offs

- [初期運用負荷増] → テンプレート化されたrulesで記述負荷を抑制
- [規約の過剰厳格化] → 実験速度が落ちる場合はspec更新で見直し可能にする
- [規約逸脱の見逃し] → tasksに整合性確認タスクを常設しレビューで補完
- [自動化の権限過多] → 最小権限トークンとPR必須の二重ガードを適用

## Migration Plan

1. OpenSpec configへ規約を反映
2. 規約specを追加し、受け入れ条件を固定
3. 新規変更から当規約を適用、必要に応じて追補改定
